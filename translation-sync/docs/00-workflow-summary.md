# 번역 동기화 워크플로우 총괄 설계

## 1. 목적

번역 동기화 워크플로우의 전체 단계 순서, 실패 시 회귀 경로, git 반영 조건을 규범적으로 정의한다.

## 2. 범위

이 문서는 다음만 소유한다.

- 동기화 단계의 실행 순서와 의존 관계
- 실패 시 회귀 단계의 결정 규칙
- 산출물의 git 반영 조건

단계별 세부 설계는 각 단계 문서가 소유한다.

| 순서 | 단계 | 기준 문서 |
|---:|------|----------|
| 0 | 원문 기준 고정·동기화 | 이 문서의 입력·불변 조건 |
| 1 | 전처리 | [01-preprocessing.md](01-preprocessing.md) |
| 2 | effective delta·변경 계획·번역 | [02-translation.md](02-translation.md) |
| 3 | 후처리 | [03-postprocessing.md](03-postprocessing.md) |
| 4 | 문서 검증 | [04-verification.md](04-verification.md) |
| 5 | 사이드바 갱신·검증 | [06-sidebar-sync.md](06-sidebar-sync.md) |
| 6 | 사이트·산출 경로 검증 | [05-additional-work.md](05-additional-work.md) |
| 7 | git 반영 | [05-additional-work.md](05-additional-work.md) |

오류 분류와 복구 정책은 [08-error-cases.md](08-error-cases.md)가 소유한다.

## 3. 입력

| 항목 | 설명 |
|------|------|
| upstream 원문 저장소 | 버전별 영어 Markdown 원문 |
| upstream manifest | 버전별 commit SHA를 기록한 JSON |
| 기존 locale 문서 | 한국어·일본어 번역 문서 |
| `versions.json` | 처리 대상 버전 목록 |
| `documentation.md` | 버전별 사이드바 기준 원문 |
| 번역 프롬프트 | locale별 번역 지침 |

## 4. 출력

| 항목 | 설명 |
|------|------|
| 갱신된 영어 원문 캐시 | manifest SHA 기준으로 동기화된 원문 |
| 갱신된 locale 문서 | 변경 diff가 반영된 한국어·일본어 문서 |
| 갱신된 사이드바 JSON | `documentation.md` 기준으로 재생성된 sidebar |
| 실행 브랜치 커밋 | 모든 검증을 통과한 변경분 |

## 5. 불변 조건

1. 단계는 정해진 순서대로 실행해야 한다. 순서를 건너뛰거나 역행해서는 안 된다.
2. 한 단계가 실패하면 후속 단계를 실행해서는 안 된다.
3. 모든 검증을 통과하지 않은 산출물을 커밋해서는 안 된다.
4. 같은 워크플로우 실행에서 replay와 live 실행은 동일한 upstream manifest SHA를 사용해야 한다.
5. 실패와 무관한 단계의 산출물을 임의로 재생성해서는 안 된다.

## 6. 단계 순서

```text
단위 테스트 → identity replay·upstream SHA manifest 확정 → 같은 SHA 2차 replay(새 프로세스 수렴 확인) → live provider fixture 계약 검사 → 동일 manifest로 원문 동기화 → 이전·현재 원문 전처리 → effective delta·변경 계획 생성 → 소유 단위 번역·후처리 → locale 문서 검증 → 사이드바 갱신·검증 → 사이트·산출 경로 검증 → 실행 브랜치 반영
```

## 7. 회귀 규칙

실패 시 자동 회귀 루프를 수행하지 않는다. 실패 원인을 수정한 뒤 해당 단계부터 워크플로우를 다시 실행해야 한다.

| 실패 발생 단계 | 실패 원인 | 되돌아갈 단계 |
|---------------|-----------|--------------|
| 검증 | 전처리 누락 | 전처리 |
| 검증 | 구조 손상 응답·번역 누락 | 번역 |
| 검증 | 후처리 형식 오류 | 후처리 |
| 검증 | 사이드바 항목 누락·라벨 불일치·locale sidebar JSON 잔존 | 사이드바 갱신 |
| 최종 산출 | 산출 기준 미달 | 검증 |

회귀 원칙:

- 회귀한 단계에서 원인을 해소한 뒤, 후속 단계를 순서대로 다시 진행해야 한다.
- 번역으로 회귀한 경우 해당 블록을 재처리한 뒤 후처리와 검증을 다시 실행해야 한다.
- 회귀 중 원인과 무관한 단계의 산출물을 변경해서는 안 된다.

### 7.1 provider 재시도 경계

동일 블록의 provider 응답 평가는 최초 요청을 포함하여 최대 2회까지 수행할 수 있다. 각 평가의 transport 호출은 일시 오류에 한해 최대 3회 시도할 수 있다. 따라서 블록당 물리 provider 호출 상한은 6회다.

## 8. git 반영 조건

1. 문서 검증, 사이드바 검증, 사이트 검증, 산출 경로 검증이 모두 통과해야만 커밋해야 한다.
2. 검증이 하나라도 실패하면 어떤 변경도 커밋해서는 안 된다.
3. 반영할 변경분이 없으면 빈 커밋을 만들어서는 안 된다.
4. 변경분은 워크플로우를 실행한 브랜치에 커밋해야 한다.
5. `main` 브랜치 실행 결과만 배포를 트리거해야 한다.
6. branch가 아닌 ref(tag 등)에서의 실행은 초기에 거부해야 한다.
7. checkout은 write credential을 저장해서는 안 된다. push credential은 모든 검증과 커밋이 끝난 별도 push 단계에서만 설정해야 한다.
8. Pull Request를 자동 생성해서는 안 된다. 실행 브랜치에 직접 push해야 한다.

세부 반영 기준은 [05-additional-work.md](05-additional-work.md)의 산출 검증 설계를 따른다.

## 9. 수용 기준

- 모든 단계가 정의된 순서대로 실행되고 있음을 확인할 수 있어야 한다.
- 실패 시 정확한 회귀 대상 단계를 식별할 수 있어야 한다.
- git 반영 조건을 만족하지 않는 커밋이 존재해서는 안 된다.
- replay와 live 실행이 동일한 upstream SHA를 사용하고 있음을 manifest로 증명할 수 있어야 한다.
